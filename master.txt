2. EXECUTIVE DIAGNOSIS (THE 12 THINGS THAT MATTER MOST)
======================================================================

1. [VERIFIED] The API Keys page cannot open. middleware.ts has a permanent 301 redirect:
   "/dashboard/keys": "/dashboard". The dashboard "API Keys" button and the link in /docs both point to
   /dashboard/keys, so users bounce back to the dashboard. Because it is a 301, browsers cache it, so the bug
   survives even after the code is fixed (test in a private window or clear cache).

2. [VERIFIED] The site's central promise is "permanent 301 redirects". That conflicts with the product features
   it sells: click tracking, editable QR destinations, one-time links, click caps, expiry, password gates,
   geo/device targeting, A/B splits. A browser-cacheable 301 means repeat clicks never reach your server, so they
   are never counted and destination edits do not take effect. [HYPOTHESIS] This is a major cause of
   "tracking doesn't work". Test in section 4.

3. [VERIFIED] middleware.ts runs Clerk on every request, including /r/* short-link redirects. That adds latency
   and a failure point to the hottest path. It also makes the "sub-15ms redirect" claim impossible.

4. [VERIFIED] Identity confusion. The homepage sells a link manager, then an expense splitter, a UPI QR generator,
   a PDF scanner, pomodoro, ambient sounds, etc. Bitly, TinyURL and Cuttly never do this. It weakens trust and
   dilutes search relevance. It also pulls an India-specific tool (UPI) into a site that wants US users.

5. [VERIFIED] Unprovable or inconsistent claims on public pages (details in section 10): "99.99% uptime
   guarantee", "<15ms latency", "increase CTR by 34%", competitor price/latency numbers, "24/7 dedicated support"
   at $9/mo, "Webhooks for scan events" (not in README), "100% free forever" vs paid plans.

6. [VERIFIED] Pricing is inconsistent. The Free plan card lists paid features (A/B splits, geo targeting, password
   protection, CSV export) while the comparison table says Free has none of them. README says Stripe and ~$2/$6;
   pricing page says $3/$9 and links to a Polar.sh portal. Homepage says "Free limit: Unlimited" while pricing
   says 1 domain short link.

7. [VERIFIED] API docs and README disagree: docs use header "Authorization: Bearer" and field "longUrl";
   README uses header "x-api-key" and field "url". One of them is wrong for developers.

8. [VERIFIED] Visual "AI tells" (section 6): icon on every nav item, tinted icon chips, rounded pill buttons with
   arrows everywhere, bold-lead bullet lists with " - " dashes, hype copy ("Enterprise-grade", "Next-Gen",
   "Infrastructure Built For..."), a wall of directory badges, flag emojis, an oversized footer.
   The Product Hunt badge shows "2" votes, which hurts credibility more than it helps.

9. [VERIFIED] The dashboard is dull and incomplete: a large admin-promo banner ("Marketing Link Engine") dominates
   the top; 7 pill buttons wrap and orphan "Marketing Links" on a second row; the link list has no copy button,
   no search, no sorting, no filters, no tags, no QR shortcut, unlabeled icon-only actions, and a trash icon with
   no visible confirmation. Admin tools ("SEO & Search Console", "Marketing Links") appear in the customer UI.

10. [VERIFIED] Abuse/safety risk. The first link in the dashboard shortens ul0.site itself (a loop), another points
    to pastebin.com. Shorteners on cheap TLDs get blocklisted fast. If ul0.site gets flagged by Google Safe
    Browsing or email filters, everything else stops mattering. (Section 14.)

11. [VERIFIED] Ad-gated "Marketing Link Engine" (content gates, 5s auto-skip). Interstitial ad gates make a
    shortener look like spam to users, browsers and ad networks. Keep it admin-only, noindex, and away from the
    brand until the core product is trusted. Consider removing it.

12. [VERIFIED] The competitive claim is "Free, unlimited, no limits" while selling Pro/Business. You will not
    out-feature Bitly. You can win on: free custom domain, privacy-first analytics, honest pricing, open source,
    clean developer API, and a calmer, faster UI. Build the brand around those, not around "we are bigger".

4. TRACKING & ANALYTICS REBUILD
======================================================================

Evidence: dashboard shows 20 links, 33 total clicks; a link created 10/8 shows 0 clicks; others show 2 and 6.
User reports tracking "does not work properly". Code not visible, so investigate in this order.

4.1 Diagnose (write findings into the PR description)
Check each hypothesis and mark confirmed/rejected:

H1 Redirect is a cacheable 301.
   Test: curl -sI https://ul0.site/r/<slug>. Look at status and Cache-Control.
   Then open the short link twice in the same browser with DevTools Network open. If the second request says
   "(from disk cache)" or never hits the server, repeat clicks are lost.

H2 Redis cache-hit path skips click logging.
   Common bug: cache hit -> redirect immediately, click logging only runs on cache miss.
   Test: click a link twice; compare Redis hit logs vs Appwrite click rows.

H3 Click logging is fire-and-forget and gets killed.
   On Vercel, un-awaited promises after the response can be cancelled. Use after() from "next/server"
   (or waitUntil) so logging finishes after the redirect is sent.

H4 Custom-domain path.
   middleware rewrites custom-domain slugs to /r/<slug>. Confirm the click row records the correct host,
   linkId and owner, and that dashboard queries include custom-domain clicks.

H5 Dashboard aggregation bugs.
   - Appwrite listDocuments returns 25 rows by default. Any "total clicks" computed from a default page is wrong
     once data grows. Use Query.limit and the response "total", or keep counters.
   - Time zone: "today/yesterday" must use one explicit time zone (store UTC, display in user's zone).
   - Per-link count vs total count computed by different code paths.

H6 Bots and prefetchers.
   Link-preview bots (WhatsApp, Slack, Facebook, Google, Bing, uptime monitors) either inflate counts or,
   if filtered badly, hide real clicks. Decide and implement a clear rule (4.3).

H7 Missing indexes or schema limits in Appwrite causing silent write failures or timeouts.
   Check server logs for rejected writes, rate limits, or attribute size errors.

4.2 Redirect behavior (decision)
- Default for all links: HTTP 307 or 302 with  Cache-Control: no-store  (or private, max-age=0).
  This makes counting, edits, expiry, passwords, geo rules and A/B splits actually work.
- Offer "Permanent (301)" as an optional per-link setting for SEO-only use, with a visible note that clicks
  from repeat visitors may not be counted.
- Rewrite the marketing copy to match: do not sell "301 equity" as the headline.
  Shortener URLs are noindexed; the equity claim is weak and risky.

4.3 Event pipeline (target design)
On every redirect (including cache hits):
1. Resolve slug from Redis (fallback Appwrite, then re-warm Redis).
2. Evaluate rules in order: disabled/expired/click-cap -> password gate -> geo/device rules -> A/B choice.
3. Send the redirect immediately.
4. In after(): write one click event. Never block the redirect on analytics.

Click event fields:
  linkId, ownerId, host, slug, ts (UTC), country, region, city (optional),
  device (mobile/tablet/desktop), os, browser, referrerHost, utm_source/medium/campaign/term/content,
  language, isBot, visitorHash, isUnique(day).

Geo: use Vercel headers x-vercel-ip-country, x-vercel-ip-country-region, x-vercel-ip-city.
Do not store raw IPs.
Unique visitors: visitorHash = SHA-256(dailySalt + ip + userAgent), salt rotated daily and never stored with
the data. No cookies. This keeps the "privacy-first, no cookies" promise true.
Bots: use the `isbot` package plus an allowlist of preview bots. Store isBot=true, exclude from default
dashboard totals, add a "show bots" toggle.

4.4 Aggregation
- Keep a real-time counter in Redis (INCR per link per hour) for fast "live" numbers.
- Roll up to a daily collection: (linkId, date) -> clicks, uniques, per-country, per-device, per-referrer maps.
- Dashboard charts read the rollups, not raw events. Raw events remain for drill-down and CSV export.
- Retention: raw events 13 months on paid plans, 30 days on free (state this on pricing).

4.5 Acceptance tests for tracking
[ ] Click a new link 5 times in one browser: dashboard shows 5 total within a few seconds.
[ ] Click from phone and desktop: device split shows both.
[ ] Click with ?utm_source=test: appears under UTM sources.
[ ] Click through a custom domain: counted under the right link.
[ ] Expired / password / click-cap / one-time links behave correctly and log the right outcome.
[ ] Edit the destination: next click goes to the new destination immediately.
[ ] Bot user-agent (curl with Slackbot UA): flagged, excluded from default totals.
[ ] Total clicks on dashboard = sum of per-link clicks for the same date range, always.
[ ] Kill-test: simulate slow DB; redirect still returns in under 100 ms.
[ ] Add an automated integration test for each of the above where possible.

6. DESIGN SYSTEM (APPLE / NOTION / LINEAR FEEL, NOT "AI GENERATED")
======================================================================

Reference products to study before designing: Dub.co (closest competitor), Linear, Vercel, Notion, Apple.com,
Stripe Docs, Raycast. Bitly, TinyURL and Cuttly are the market reference for familiar patterns,
not for visual quality.

6.1 Principles
- Quiet. Content first. One accent color. Whitespace does the work, not boxes and shadows.
- Hairline borders instead of heavy shadows. Almost flat.
- Consistent: one type scale, one spacing scale, one radius set, one icon set.
- Real product screenshots instead of illustrations and icon chips.
- Plain, specific copy. Say what the product does. No superlatives.

6.2 What currently reads as AI-generated (remove these)
[ ] Icons on every top-nav item. Nav should be text only.
[ ] Tinted square icon chips (green/blue/purple) in cards and stats.
[ ] Arrow glyphs on every button and link ("Manage Domains ->", "Open Marketing Engine ->").
[ ] Heavy 800-weight headlines. Use 600 with tight tracking.
[ ] Bullet lists with bold lead-in and " - " dash explanations.
[ ] Words: "Enterprise-grade", "Next-Gen", "Infrastructure Built for...", "Engineered for...", "Modern Teams".
[ ] Directory badge wall ("Featured on trusted directories") and SEO paragraph blocks on the homepage.
[ ] Flag emojis in the footer language list.
[ ] A 40-link footer.
[ ] The "$" inside the logo mark (signals ad monetization). Use a clean mark.
[ ] Gradients, glows, glassmorphism, blobs, animated gradients.

6.3 Tokens (adjust accent to the logo's exact teal-green)
Colors, light:
  --bg #FFFFFF   --surface #FAFAFA   --surface-2 #F4F4F5
  --border rgba(0,0,0,0.08)   --border-strong rgba(0,0,0,0.14)
  --text #0A0A0B   --text-muted #6B6B72   --text-faint #9A9AA2
  --accent #12926E (derive from logo)   --accent-hover darker 8%   --danger #D92D20   --warn #B54708   --ok #067647
Colors, dark:
  --bg #0B0B0C   --surface #111113   --surface-2 #18181B
  --border rgba(255,255,255,0.08)   --text #F4F4F5   --text-muted #A1A1AA
Support light and dark from day one (prefers-color-scheme + manual toggle).

Typography:
  Inter (variable, self-hosted via next/font) or Geist. One family.
  Marketing: H1 56/60 (mobile 36/40) weight 600 tracking -0.03em; H2 36/42; H3 20/28; body 17/28 muted.
  App: 14/20 body, 13 secondary, 12 captions, 24/32 page titles. Tabular numbers for all metrics.
  Mono (Geist Mono or JetBrains Mono) only for short links, API keys, code.

Spacing: 4px base; use 4, 8, 12, 16, 24, 32, 48, 72, 112.
Radius: 8 (inputs, buttons), 12 (cards, popovers), 9999 only for tiny badges.
Borders: 1px. Shadows: only on popovers/menus (0 8px 24px rgba(0,0,0,0.08)).
Max content width: 1120 marketing, 1280 app. Marketing sections use 112px vertical rhythm on desktop.

Motion: 120-200ms, ease-out, opacity/translate only. Respect prefers-reduced-motion.
Loading: skeletons, never spinners on full pages. Toasts for success/failure. Optimistic updates.

Buttons: primary (solid text color or accent), secondary (border), ghost. 36px app height, 44px marketing.
No arrows inside buttons except on explicit "next" actions.

Icons: ONE set. Use Lucide at strokeWidth 1.5 (or Phosphor Regular). 16px in app, 18px in marketing.
Rules: icons only where they speed recognition (copy, QR, analytics, delete, external link, search, settings).
Never decorative. Never inside colored chips. Always paired with an aria-label or tooltip when icon-only.
Replace all currently mixed icon styles so strokes match. Logo: redraw as a simple monochrome mark
that works at 16px favicon, with a light and dark variant.

6.4 Component rules (shadcn/ui, restyled with the tokens above)
- Tables: 44px rows, hairline row dividers, hover background surface, sticky header, sortable columns.
- Cards: border only, 12px radius, no shadow, 20-24px padding.
- Inputs: 36-40px, 1px border, accent focus ring (2px, offset 2px).
- Command palette (Cmd/Ctrl-K): search links, jump to pages, create link.
- Empty states: one sentence, one primary action, optional small screenshot.
- Confirm dialogs for destructive actions, with undo toast where possible.

19.2 LINK-GENERATION ANIMATION (HOMEPAGE HERO + DASHBOARD)
----------------------------------------------------------------------
Goal: shortening a link should feel like a small moment of delight, in under 700ms, without ever delaying the real result.

Sequence (homepage):
  0 ms       Click Shorten. Button label swaps to a thin progress bar (no spinner). A 2px teal line sweeps across
             the bottom of the input (150ms).
  60-350 ms  "Compress": the long URL text clips and scales down toward the output slot while fading
             (transform + opacity only).
  200-520 ms Result card rises in (translateY 8px to 0, opacity 0 to 1, spring: stiffness 320, damping 28).
             The short link types in character by character in the mono font (stagger 16ms per character).
  350-600 ms A check mark draws with an SVG stroke (stroke-dashoffset, 220ms) next to the link.
  400-800 ms If a QR is shown: modules fade in as a diagonal wave (stagger by x+y, total 400ms).
  After      Copy button gets focus. Click: label morphs "Copy" to "Copied" with a check, reverts after 1.6s.
             On mobile: navigator.vibrate(10) if available. Never auto-copy without a setting.
Rules:
  - Show the real result the moment the API returns. The animation has a minimum duration of about 350ms but
    never waits on the network twice.
  - Error: input shakes (two 4px cycles, 240ms) and a human message appears under it. No red flashing.
  - prefers-reduced-motion: swap instantly, no typing, no wave, no shake (use a color fade only).
  - Implement with CSS transitions and the Web Animations API first. Use the "motion" (Framer Motion) library only
    if needed, in a lazy-loaded client component. Total animation JS budget: under 25 KB gzipped.

Dashboard create flow:
  - Create happens in the right-side drawer. On success the drawer shows the same compress-to-link animation,
    then closes after the user copies or presses Done.
  - The new row slides into the top of the table and its background pulses teal-500 at 12% fading to 0 over 1.2s.
  - Very first link ever: a small, tasteful burst of about 14 teal/coin particles for 600ms. Never again after that.
  - Quick-create: Cmd/Ctrl-K then paste a URL then Enter creates a link without leaving the page.
  - Paste detection: if the clipboard contains a URL when the user focuses the field, offer a "Paste URL" chip.

20.2 CLAIM SYSTEM (HOW ANONYMOUS LINKS BECOME ACCOUNT LINKS)
----------------------------------------------------------------------
Rules:
- Anonymous links always work immediately and permanently, claimed or not.
- Clicks are recorded from the very first click (cheap, privacy-friendly, see section 4), whether or not the link is claimed.
  After claiming, the owner sees the history, nothing is lost.
- Only the browser that created the link (or someone holding its claim link) can claim it.

Flow:
1. Create: POST /api/shorten { url, slug?, withQr?: boolean } as anonymous.
   Server creates the link with ownerId = null, source = "anon", and a random claim token (32 bytes).
   Store only a hash of the token in the database. Return the raw token once.
2. Browser keeps the token in an httpOnly, Secure, SameSite=Lax cookie (a signed list of {linkId, token}, max 20 entries,
   30-day expiry) and ALSO stores a non-secret list of {linkId, shortUrl} in localStorage for the "recent links" UI.
   Never put the raw token in localStorage.
3. Show the claim banner (20.3). "Claim" starts Clerk sign-in (Google one tap or button) and returns to the homepage with ?claim=1.
4. After sign-in, the page calls POST /api/links/claim (authenticated). The server reads the cookie, verifies each token hash,
   confirms the link is unclaimed and under 30 days old, sets ownerId = current user, claimedAt = now, clears the token hash,
   and removes claimed items from the cookie. Idempotent: calling twice is safe.
5. Redirect the user to the link detail page in the dashboard with a "Link claimed" toast and the entrance animation.
6. Lost cookie fallback: the result card offers "Copy claim link" (https://ul0.site/claim/<token>) so the user can claim from
   another device or after clearing cookies. The claim page requires sign-in, then applies the same server checks.
7. Expiry: unclaimed tokens expire after 30 days. After that the link keeps working but can no longer be claimed or edited.
8. Plan limits on claim: anonymous public-domain links do not count toward custom-domain limits. If a limit would be exceeded,
   claim as many as fit, tell the user which were not claimed, and explain the options (no data is deleted).
9. Abuse: rate limit /api/links/claim per user and per IP. Log every claim (userId, linkId, time).

[ ] The QR encodes the SHORT link, never the destination. This is what makes it "dynamic" and trackable.
